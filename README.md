# B4. Blocking / Non-Blocking · Sync / Async

> 발표자: 강민아
> 목표: 두 개념을 구분하고, **실무에서 언제 동기/비동기로, 언제 블로킹으로 처리해야 하는지**를 코드 예시로 판단할 수 있게 한다.

---

## 목차

### 1. 들어가며
- 이 주제를 고른 이유
  - 축구에서 블로킹: 수비수가 공격수를 막음 → 그럼 컴퓨터에서 블로킹은 **무엇을 막을까?**
  - 휴대폰 동기화: 휴대폰과 컴퓨터의 데이터를 맞춤 → 그럼 개발자가 말하는 동기는 **무엇을 맞출까?**
  - 개발하면서 자주 듣지만, 막상 정확히 설명하기는 어려웠던 두 단어
- 오늘 알아볼 것
  1. 블로킹은 무엇을 막는가, 동기는 무엇을 맞추는가 → 2장
  2. 코드에서는 어떻게 보이는가 → 3장
  3. 실무에서 언제 기다리고, 언제 기다리지 말아야 하는가 → 4~6장
- 답 (2장에서 공개)
  - 블로킹은 **스레드가 다음 줄로 나아가는 것**을 막는다
  - 동기는 **작업이 끝나는 시점에 맞춰** 내가 직접 결과를 챙기는 것 (同期, Synchronous = "같은 시간")

### 2. 핵심 개념 정리
- 2.1 블로킹은 왜 생겼을까
  - 출발점: CPU는 나노초 단위, I/O 장치(디스크·네트워크)는 수천~수백만 배 느림 → 결과가 올 때까지 다음 명령을 진행할 수 없음
  - 초기 방식: 바쁜 대기(Busy Waiting) → CPU가 "끝났나?"를 계속 확인, 실제로 한 일은 없음
  - 해결: 인터럽트 + 멀티프로그래밍 → 기다리는 스레드는 대기(Blocked) 상태로, CPU는 다른 스레드 실행, 결과가 오면 다시 깨움
  - 그래서 블로킹은 무엇을 막을까?
    - 축구: 수비수가 공격수가 **앞으로 나아가는 것**을 막음
    - 컴퓨터: I/O 결과가 올 때까지 **스레드가 다음 줄로 나아가는 것**을 막음 (CPU는 막히지 않음)
- 2.2 동기·비동기는 어떻게 나왔을까
  - 처음에는 모든 호출이 "블로킹 + 동기": `data = read(file)` → 멈춤 → 다음 줄에서 바로 사용
  - 블로킹의 한계(기다리는 스레드 증가) → 논블로킹 등장: "아직 없음"을 바로 받고 돌아옴
  - 그럼 데이터가 왔다는 걸 스레드가 어떻게 알까? 논블로킹이라는 말만으로는 이걸 정해주지 않음 → 방법은 두 가지
    1. 스레드가 직접 다시 물어보기: 다른 일을 하다가 중간중간 "이제 왔어?" 하고 다시 확인 → **논블로킹 + 동기**
    2. 다 되면 알려주기: 스레드는 자기 일을 하고, 데이터가 준비되면 시스템이 콜백·이벤트로 알려줌 → **논블로킹 + 비동기**
- 2.3 두 축은 서로 다른 질문: 2×2 매트릭스
  | | Blocking | Non-Blocking |
  |---|---|---|
  | **Sync** | 일반적인 메서드 호출, JDBC 쿼리 | 폴링(완료됐는지 계속 확인) |
  | **Async** | 비동기로 맡기고 바로 결과를 기다림 (흔한 실수) | 콜백·Future·이벤트 기반 처리 |
  - "비동기 = 논블로킹"이 아닌 이유: 비동기로 맡기고 바로 `future.get()`으로 기다리면 결국 블로킹

### 3. 코드로 보기 (Java / Spring Boot 중심, 예제: [`FourCombinations.java`](demo/src/main/java/com/sortech/b4demo/chapter3/FourCombinations.java))
- 3.1 동기 (Sync): 호출한 쪽이 결과를 직접 챙김
  - Sync + Blocking: `restTemplate.getForObject()` → 이 줄에서 멈추고, 다음 줄에서 바로 결과 사용 (JDBC·파일 읽기도 같음)
  - Sync + Non-Blocking: `pool.submit()`으로 맡기고 바로 돌아옴 → `while (!future.isDone())`으로 "이제 왔어?" 직접 확인 (폴링)
- 3.2 비동기 (Async): 작업이 끝나면 알려줌
  - Async + Non-Blocking: `supplyAsync(...).thenAccept(...)` 콜백 등록 → 기다리지 않고 다음 일 (`@Async`, `WebClient.subscribe()`)
  - Async + Blocking: 비동기로 맡기고 바로 `future.get()` / `.block()` → 결국 멈춤 (흔한 실수)
- 3.3 프론트엔드에서는?: 질문은 백엔드와 같음 (순서가 중요한가? 동시에 하면 꼬이는가? 결과를 바로 써야 하는가?)
  - 순서가 중요할 때 → 순서대로 `await` (로그인 → 내 정보 → 내 주문)
  - 동시에 하면 꼬일 때 → 두 번째 요청 막기 (결제 버튼 연타 방지: 처리 중 플래그, 버튼 비활성화)
  | 상황 | Java (백엔드) | JavaScript (프론트엔드) |
  |---|---|---|
  | 순서가 중요함 | 순서대로 호출 (동기) | `await`을 순서대로 |
  | 동시에 하면 꼬임 | `synchronized`, DB 락 | 처리 중 플래그, 버튼 비활성화 |
  | 서로 관계없음 | `CompletableFuture.allOf` | `Promise.all` |
  | 반드시 멈춰야 함 | `future.get()` | `confirm()` (드묾) |
  - 프론트엔드는 메인 스레드가 하나라서 비동기를 기본 방식으로 쓰고, "스레드를 멈추는 방법" 대신 "순서대로 await하기"와 "두 번째 요청 막기"로 같은 목적을 이룸
- 3.4 프론트엔드: 기다리는 일 vs 계산하는 일
  - 기다리는 일(타이머·네트워크·이벤트) → 브라우저에 맡기고 바로 돌아옴 (비동기)
    - 예: "장바구니에 담았습니다" 알림을 `setTimeout`으로 3초 뒤 닫기 / 반복문으로 직접 기다리면 3초 동안 화면 멈춤(바쁜 대기)
    - 실무: 알림 자동 닫기, 자동 로그아웃 경고, 검색어 자동완성, 카운트다운
  - 계산하는 일(데이터 정리) → CPU가 계속 일하는 중이라 동기, 많으면 화면 멈춤
    - 예: 상품 10만 개 `filter`·`sort` / 해결: Web Worker(다른 스레드)에 `postMessage`로 맡기고 `onmessage`로 결과 받기
    - 실무: 엑셀 업로드 검사, 대시보드 집계, 이미지 압축, 긴 목록 검색

### 4. 실무 문제, 코드로 해결하기 (데모: [`demo/`](demo/README.md))
- 도입: 이런 문제를 겪어본 적 있나요? → 1·2번은 블로킹이 **원인**, 3번은 블로킹이 **해결책**
- 4.1 응답이 느림: 외부 API 3개 순차 호출(약 3초) → `CompletableFuture.allOf`로 동시 호출(약 1초)
- 4.2 서버가 멈춤: 타임아웃 없는 호출로 스레드 풀 고갈 → 타임아웃 설정(+ 스레드 풀 분리, 서킷 브레이커, WebClient)
- 4.3 데이터가 꼬임: 락 없는 재고 차감(재고 0이 아님) → `synchronized` / `SELECT ... FOR UPDATE` / 분산 락
- 진행 방식: 문제 코드 실행 → 해결 코드 실행 → 결과 숫자 비교

### 5. 언제 무엇을 쓸까
- **동기로 처리해야 하는 경우**: 순서가 보장되어야 하는 작업 (예: 주문 → 결제 → 재고 차감)
- **블로킹이 필요한 경우**: 다른 요청의 접근을 막아야 할 때 (동시성 제어)
- **비동기·병렬로 처리해도 되는 경우**: 알림/메일 발송, 로그 적재, 관계없는 외부 API 동시 호출, 메시지 큐(Kafka)

### 6. 주의할 점: 일을 다른 스레드에 맡기면 생기는 문제 5가지
| 주의할 점 | 무슨 일이 생기나 | 이렇게 막아요 |
|---|---|---|
| ① 스레드 풀 고갈 | 스레드가 전부 느린 API를 기다려서 다른 요청을 못 받음 | 타임아웃, 스레드 풀 나누기 |
| ② 비동기 예외 처리 | 다른 스레드의 오류라 내 try-catch에 안 잡힘 | `exceptionally()`로 실패 처리 |
| ③ 블로킹 섞기 | 기다리면 안 되는 적은 수의 스레드(WebFlux)가 DB를 기다림 | R2DBC 또는 별도 스레드 풀 |
| ④ `@Async` 내부 호출 | 같은 클래스 안에서 부르면 비동기가 안 걸리고 그냥 기다림 | 다른 클래스로 옮기기 |
| ⑤ 로그 추적 | 스레드가 바뀌어서 어느 요청의 로그인지 모름 | 요청마다 번호(요청 ID) 붙이기 |

- 다섯 가지 모두 일을 다른 스레드에 맡기는 순간 생김 → 맡길 때는 시간 제한, 실패 처리, 추적 번호를 같이 챙기기
